# Совместная разработка

Участие в разработке приветствуется. Этот пакет содержит независимую учебную часть; доработки должны оставаться в её описанных границах.

## Чтение кода и принятие изменений

Apache 2.0 позволяет читать, использовать и форкать опубликованный код без статуса разработчика. Открытие предложения в GitHub само по себе не выдаёт такой статус и не гарантирует принятие.

**Администратор не принимает GitHub-изменения автора без подтверждённого статуса разработчика.** Статус выдаётся после заявки, верификации и отдельного одобрения. Привязка проверяется по неизменяемому числовому GitHub ID, а не по введённому имени или одному только текущему login.

Реестр статусов и проверки находятся вне этого учебного пакета. Пока способ верификации не согласован или статус невозможно проверить, предложение не принимается. Наличие статуса не даёт прав на админку, рабочую среду, выпуск, секреты или личные данные.

Перед принятием проверяется действующий статус автора конкретного предложения и конкретная версия предлагаемых изменений. Новые коммиты после проверки требуют повторной проверки. Отозванный или отсутствующий статус не считается разрешением; предыдущая проверка его не заменяет.

## С чего начать

1. Прочитайте [архитектуру](docs/architecture.md), [модель данных](docs/data-model.md) и [API](docs/api.md).
2. Запустите локальную демонстрацию с вымышленными данными по [инструкции](docs/development.md).
3. Обсудите проблему и ожидаемое поведение, особенно если меняется контракт или схема.
4. Вносите небольшую связанную правку и добавляйте тесты поведения, которое она меняет.
5. В предложении укажите проблему, результат, способ проверки и ограничения.

Правки интерфейса следует проверить на узком и широком экране, с клавиатурой и длинными названиями. Изменения API должны сохранять документированные ошибки и правила версий либо явно описывать несовместимость.

## Что можно добавлять

- Улучшения учебной модели и её проверок.
- Изменения локального интерфейса и доступности.
- Надёжность версионирования, экспорта и удаления точных повторов.
- Документацию и тесты на вымышленных примерах.

Нельзя добавлять личные записи, рабочие базы, реальные учётные данные, внутренние адреса, дампы, скриншоты аккаунтов или файлы пользователей. Закрытые интеграции, административные полномочия и выпуск не переносятся сюда ради удобства тестирования.

## Проверки перед предложением

```sh
PYTHONPATH=src python3 -m unittest discover -s tests -v
```

Не исправляйте уже применённую SQL-миграцию: создайте следующую. Если меняются поля, ограничения или маршруты, обновите соответствующую документацию. Данные примеров не должны выглядеть как актуальное расписание или настоящие оценки.

Не включайте в предложение сгенерированную базу, виртуальное окружение, журналы или локальные настройки. Сообщения об уязвимостях направляйте согласно [SECURITY.md](SECURITY.md), без публичного раскрытия секретов.
